## 0. Assessment — are these four PRs worthwhile for v0.7.2?

**Verdict: all four are worthwhile, but not equal. #26 and #27 are defect fixes that should gate v0.7.2. #28 is a small, clean feature worth taking. #29 is the only one worth considering for deferral.**

| PR | Ship in v0.7.2? | Rationale |
|----|-----------------|-----------|
| #26 | **Yes — required** | Double-apply data bug; silent wrong action |
| #27 | **Yes — required** | Breaks the default feature's core promise |
| #28 | **Yes** | Small, fixes wrong-browser steering, prerequisite for #29 |
| #29 | **Yes only if** #28 lands first and single-flight + bounded-wait tests exist; otherwise defer to v0.7.3 | Highest-risk surface; no correctness bug forcing it now |

### #26 — highest value
Only PR addressing a correctness bug with a data-integrity tail. The hang is
user-visible, but the real problem is the double-apply hazard: the click stays
queued server-side and fires when the tab wakes, so the caller's
timeout-driven retry clicks **twice** — a silent wrong-action class of bug,
the worst kind for an automation tool. Verified gap: `content.js:1100-1107`
awaits an unbounded RAF promise; `content.js:753-756` sits inside a bounded
loop but each iteration can still stall. Regression risk low: hang → bounded
settle, existing 43-test suite covers the click/readiness paths.

### #27 — user trust
The symptom directly contradicts the feature's promise: "Reuse current
window" is the **default**, and the adoption design (`background.js:1151-1228`,
`:1637-1646`) exists to prove Claudezilla won't disturb the user's window —
yet every second `firefox_create_window` yanks the user's visible tab. That
undermines the flagship politeness guarantee of the default configuration.
Fix is a one-branch `active` decision, scoped to `adopted: true` windows.

### #28 — small, and it unblocks #29
Status-quo failure is nasty: two extension-carrying browsers → last-started
host silently steals the socket → MCP drives the **wrong browser**. Not a
niche multi-browser scenario — it is the default outcome of opening a second
profile. Change is one env-var check in `getSafeTempDir()` (`host/ipc.js:89`);
all three derived paths (socket :158, token :175, debug :189) follow
automatically. Outstanding design decision: Windows named-pipe path (:154) is
hard-coded and unaffected — document POSIX-only or mirror it. **#29 is much
safer to ship after this**: autostart with a shared socket path reintroduces
exactly the wrong-browser-steers race, just triggered by a launch instead of a
connect.

### #29 — real value, highest risk
Unattended headless workflows shouldn't need a human cold-start, and
"extension not connected" as a first-call failure is poor UX. But it is the
only PR that (a) executes an arbitrary user-supplied command at tool-call
time, (b) introduces a retry-storm surface (concurrent tool calls → multiple
browser spawns without a single-flight guard), and (c) adds a new
wait/timeout state machine to the MCP request path — the same path PR #23
just finished stabilizing. Largest test burden of the four: single-flight,
timeout → original error + stderr propagation, crash-after-start retry
behavior. Defer to v0.7.3 unless those tests exist at merge time.

## 1. PR #26 — Bound animation-frame waits

**Symptom:** `firefox_click`, `firefox_wait_for`, `firefox_get_page_state`
hang until the host timeout when the target tab is not being painted (background
tab, minimized window, Wayland covered/other-workspace window). The click is
still dispatched server-side when the page wakes, so a post-timeout retry can
double-apply it.

**Root cause:** Firefox does not run `requestAnimationFrame` callbacks in a tab
the compositor is not painting.

**Observed on `main`:** the double-RAF wait pattern the PR builds on is already
in `extension/content.js`:

- Lines 753–756 (`smartQuerySelector` poll loop): `requestAnimationFrame(() =>
  requestAnimationFrame(resolve))` inside a `Date.now() - startTime < timeout`
  while-loop — bounded by the outer loop.
- Lines 1100–1108 (`checkPageReadiness`): unconditional double-RAF wait,
  measured as `result.rafWaitMs`, with **no timeout bound** — if the tab is
  unpainted this promise never resolves.

**Assessment:** the PR's claim is valid for at least the readiness path
(`content.js:1100-1107`): an unbounded `await` on RAF in an unpainted tab hangs
indefinitely. The fix should race each RAF wait against a bounded timer
(~100 ms per the PR summary) and treat expiry as "frame did not run," so
commands settle instead of hitting the host timeout. The 753–756 loop is
already bounded by its outer timeout loop but each iteration can still stall
unbounded on a single RAF — the same bound applies.

**Risk:** low. Backward compatible; changes hang → settle. Must confirm a
settled-without-RAF result does not cause the click to be dispatched twice
(the double-apply hazard the PR itself calls out).

## 2. PR #27 — Never switch the user's selected tab in an adopted window

**Symptom:** With "Reuse current window" on (default), the first agent tab
opens in the user's window in the background as intended; every later
`firefox_create_window` call switches the user's visible tab to the agent's
page.

**Root cause:** `createWindow` has two paths. The adoption path (no window
tracked yet) creates the tab with `active: false`; the existing-window path
creates every further tab with `active: true`, including when the tracked
window is the user's adopted window.

**Observed on `main` (`extension/background.js`):** the adoption framework the
PR depends on is present and verified:

- `storage.local { adoptCurrentWindow: false }` opt-out read at lines
  1155–1156; `adoptedWindow` flag set at line 1160/1169/1228.
- Window-state restore is adoption-aware (lines 81–114): only non-adopted
  windows absorb untracked tabs.
- `closeWindow` guard (lines 1637–1646): adopted windows only have Claudezilla
  tabs closed, never the user's window.

**Assessment:** the surrounding adoption machinery is correct and in place. The
specific defect — the existing-window path forcing `active: true` on subsequent
tab creations in an adopted window — is exactly the kind of branch the PR
targets. On merge, `firefox_create_window` should pass `active: false` when the
tracked window carries `adopted: true`.

**Risk:** low. Behavior change is scoped to adopted windows; dedicated
(non-adopted) Claudezilla windows keep current focus semantics.

## 3. PR #28 — `CLAUDEZILLA_IPC_DIR` socket/token override

**Motivation:** every native host binds the same socket
(`$XDG_RUNTIME_DIR/claudezilla.sock`), so with two browsers carrying the
extension the most recently started host silently takes over — the MCP server
then drives a browser the user did not expect. Use case: visible browser for
interactive work plus a headless profile for unattended jobs.

**Change:** `getSafeTempDir()` in `host/ipc.js` checks `CLAUDEZILLA_IPC_DIR`
first; when set (validated like other config vars) it overrides the default
socket/token location.

**Observed on `main`:** NOT implemented. `grep` across `host/` and `mcp/`
finds zero references to `CLAUDEZILLA_IPC_DIR`. `getSafeTempDir()`
(`host/ipc.js:89-143`) resolves in order: Windows `LOCALAPPDATA`/`TEMP`/
`tmpdir()` (each passed through `validatePath`), then `XDG_RUNTIME_DIR`, then
`~/.claudezilla/` (created `0700`), then `tmpdir()`.

**Assessment:** the override slot is clear — insert `CLAUDEZILLA_IPC_DIR` as
the first candidate before the platform branches, validated with the existing
`validatePath()` helper so path-injection parity with `XDG_RUNTIME_DIR` is
preserved. `getSocketPath()` (line 158), the token path (line 175), and the
debug log (line 189) all derive from `getSafeTempDir()`, so a single override
moves all three consistently. On Windows the named-pipe path (line 154) is
hard-coded and unaffected — the override should either be documented as
POSIX-only or mirrored into the pipe name; decide before implementing.

**Risk:** medium. Two hosts with deliberately separate dirs is the point, but
a mis-set dir means the MCP server looks at a stale socket; document the env
var alongside `CLAUDEZILLA_AGENT_TIMEOUT_MS` in README/CLAUDE.md.

## 4. PR #29 — `CLAUDEZILLA_AUTOSTART_CMD` on-demand browser start

**Motivation:** a browser used only for occasional unattended jobs need not run
constantly; today the first tool call against a stopped browser fails with
"extension not connected" and someone must start it manually.

**Change:** when `CLAUDEZILLA_AUTOSTART_CMD` is set and no host socket exists,
`sendCommand()` runs the command once and waits until the host has bound its
socket and written its token, bounded by `CLAUDEZILLA_AUTOSTART_WAIT_MS`.

**Observed on `main`:** NOT implemented. Zero references to
`CLAUDEZILLA_AUTOSTART` anywhere outside the spec files
(`PR_26-29_summary.md`, `CHECKMATE.md`).

**Assessment:** the natural implementation site is the MCP-side send path —
`mcp/socket-request.js` (extracted in PR #23) owns request/transport state, and
`mcp/server.js` dispatches commands. The launch must be single-flight (concurrent
tool calls must not spawn multiple browsers) and must run the command via
`child_process` with `shell: false` or an explicit argv split — never
interpolated shell. Success condition: socket file exists AND token file
exists AND a probe request answers; timeout → surface the original
"extension not connected" error plus the autostart command's stderr.

**Risk:** medium-high. This PR executes an arbitrary user-supplied command on
first tool call — that is by design (env var is user-controlled, same trust
domain as MCP config), but the implementation must not add shell interpolation,
and must guard against retry storms when the browser crashes after a successful
start.
